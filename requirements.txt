# OpenCV 5.0 (the current PyPI default as of this writing) removed
# CascadeClassifier from its Python bindings entirely - a real breaking
# API change, not a packaging mistake - which silently broke Wav2Lip's
# face detection (core/Wav2Lip/inference.py's face_detect()) with an
# AttributeError, on every single render, only surfacing deep into a
# render's lip-sync stage rather than at install time. Pinned below 5 to
# stay on the last API-compatible major version. opencv-python-headless
# (not opencv-python) specifically - this is a backend image-processing
# pipeline with no GUI window (cv2.imshow etc.) calls anywhere in it, and
# installing both packages side by side corrupts the shared `cv2` install
# (they ship overlapping files under the same import name) - found by
# hitting exactly that corruption for real, not assumed.
opencv-python-headless<5

# transformers>=5 removed transformers.pytorch_utils.isin_mps_friendly,
# which coqui-tts 0.27.5's XTTS loader still imports at module load time
# (an upstream coqui-tts/transformers version mismatch, not this app's
# code) - found by actually importing TTS.api and reading the real
# ImportError, not assumed. Pin below the break until coqui-tts ships a
# fix.
transformers<5

# AI & TTS Dependencies. The original `TTS` PyPI package (Coqui's,
# archived upstream) needs a C++ compiler to build its
# monotonic_align Cython extension - `Microsoft C++ Build Tools`
# aren't a given on a fresh Windows machine, and this whole tree
# doesn't need a from-source build at all. `coqui-tts` is the actively
# maintained community fork, ships a prebuilt Windows wheel (its
# monotonic-alignment-search extension is a separate prebuilt wheel
# too), and still imports as `TTS` (this codebase's import lines are
# unaffected).
coqui-tts
# Required by coqui-tts under torch>=2.9 for audio IO (a runtime
# ImportError otherwise, not a build-time one - also found by actually
# importing TTS.api, not assumed). NOTE: torchcodec needs real FFmpeg
# *shared* libraries (avcodec-*.dll etc.) - this project's own bundled
# ffmpeg/bin/ffmpeg.exe is a --enable-static build with no such DLLs,
# so TTS synthesis previously failed at runtime ("Could not load
# libtorchcodec") on every segment even though everything imported
# fine and the model loaded - each failure was logged but swallowed
# per-segment (core/tts/tts_handler.py's generate_audio()), so a whole
# render could report 100% complete with zero real dubbed audio. Fixed
# by vendoring a full-shared FFmpeg build's DLLs into ffmpeg/shared_libs/
# (gitignored alongside the rest of ffmpeg/, copied into packaged builds
# by packaging/build_dist.py's existing whole-folder ASSET_FOLDERS copy)
# and registering that folder via os.add_dll_directory() in config.py -
# plain PATH is not enough for a dependent DLL loaded via
# ctypes.CDLL(full_path) under Windows' post-3.8 safe DLL search mode.
torchcodec
